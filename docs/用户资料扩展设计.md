# 用户资料扩展设计（显示名称 / 电话 / 邮箱 / 头像 / 自助改密）

> 状态：**已实施**（见 §十二 实施记录）
> 关联需求：
> 1. 用户信息过于粗略，需要「显示名称、电话号码、电子邮件」；管理员新增用户时可填写；
> 2. 显示名称**必填**，管理员建号时默认取用户名；
> 3. 登录用户可在右上角维护自己的个人资料，并**自助修改密码**（校验原密码 + 新密码两次确认 + 审计日志）；
> 4. 自助范围内，除用户名外其余资料均可修改。
> 5. 管理员可在用户管理中**重置用户密码**（无需校验原密码，也无需二次确认）。
> 6. 支持头像：内置默认头像（初始化到对象存储），用户可自定义头像并存入对象存储；头像读取接口**匿名可访问**；
>    限制 1MB，输出 256×256，接受 jpg / png / bmp / webp / gif。

## 一、背景与目标

### 1.1 现状

用户账号实体目前只有 `username` 这一个身份字段，缺少任何"人"的信息（姓名、电话、邮箱）。

| 层面 | 位置 | 现状 |
| --- | --- | --- |
| 数据模型 | `api/app/models/system.py` 的 `User` | 字段：`id / username / password_hash / employee_id / is_active / created_at / roles`，无姓名、电话、邮箱 |
| 接口 | `api/app/api/routes/system.py` | `POST /users`、`PUT /users/{id}` 只接受 `username / password / employee_id / is_active` |
| 登录信息 | `api/app/api/routes/auth.py` 的 `GET /auth/me` | 返回 `UserOut`（含 `employee_id`），无联系方式字段、无自助修改入口 |
| 用户管理页 | `frontend/src/views/Users.vue` | 表格只有 ID / 用户名 / 角色 / 状态 / 创建时间；新增弹窗只有用户名 / 密码 / 启用 |
| 顶栏 | `frontend/src/layout/MainLayout.vue` | 右上角只显示 `userStore.username`，下拉菜单只有"角色 + 退出登录" |

### 1.2 目标

1. 用户实体增加三个字段：**显示名称（display_name，必填）**、**电话号码（phone）**、**电子邮件（email）**。
2. 管理员在「用户管理」新增 / 编辑用户时可填写这三项，列表页可直接看到；新增时显示名称默认取用户名。
3. 登录用户在右上角「个人资料」弹窗中自行维护这三项（用户名只读，其余可改）。
4. 登录用户在右上角「修改密码」弹窗中自助改密：需校验**原密码**，且**新密码输入两次并保持一致**，操作写入审计日志。
5. 管理员在「用户管理」中可对任意账号**重置密码**：只填一次新密码，不校验原密码、不做二次确认，操作写入审计日志。
6. 用户可上传自定义头像，存入对象存储（MinIO），并可从顶栏与「个人资料」弹窗看到、更换、恢复默认头像。

### 1.3 非目标（本期不做，避免范围蔓延）

- 不改变登录方式，登录凭据仍是 `username`；用户名不可自助修改（也不可由本人改）。
- 不做签名、手机验证码绑定等能力（头像见 §五）。
- **不把 `is_active`、角色、`employee_id` 纳入自助范围**：自助停用账号、自助授权限是明显的越权口子；这些字段对用户本人一律只读（理由见 §4.6）。
- 管理员重置密码**刻意不做**原密码校验与二次确认（需求明确要求），因此该能力只授予 `system:user:manage` 账号，并强制写审计日志（见 §4.4）。
- 不强制用户关联员工档案（`employee_id` 保持现状：字段已存在但界面上暂不暴露，见 §3.3）。
- 本期不做邮箱唯一性校验、邮箱找回密码、密码复杂度策略、改密后吊销其它会话（见 §八 风险）。
- 头像不做：SVG 上传、前端裁剪框（cropper）、头像历史版本与回滚、管理员替他人设置头像、GIF 动图头像（见 §5.5、§5.7）。

## 二、方案总览

一句话：**在 `users` 表就地扩四列并回填历史数据；管理侧接口做增量扩展并新增"管理员重置密码"入口；新增两个"只作用于当前登录用户"的自助接口（改资料、改密码）与一套头像能力（自助上传 + 匿名读取，图片统一规范化后存对象存储）。**

| 改动面 | 内容 |
| --- | --- |
| 数据库 | `users` 新增 `display_name VARCHAR(50)`、`phone VARCHAR(30)`、`email VARCHAR(100)`、`avatar_key VARCHAR(150)`；通过既有 `_COLUMN_MIGRATIONS` 补列，并对历史行回填 `display_name = username` |
| 后端模型 / Schema | `User` 加 4 字段（含 `avatar_key`）；`UserCreate / UserUpdate / UserOut` 扩展（`UserOut` 增加只读 `avatar_url`）；新增 `ProfileUpdate`、`PasswordChange` |
| 后端接口（管理侧） | `POST /users`、`PUT /users/{id}`、`GET /users`、`GET /users/{id}` 支持新字段，权限不变 |
| 后端接口（管理员重置密码） | 新增 `POST /users/{id}/reset-password`（单字段 `new_password`，不校验原密码、不二次确认）；`PUT /users/{id}` 的 `password` 字段保留兼容 |
| 后端接口（自助侧） | 新增 `PUT /auth/me`（改资料）、`PUT /auth/me/password`（改密码），均只要求登录 |
| 后端接口（头像） | 新增 `PUT /auth/me/avatar`（自助上传）、`DELETE /auth/me/avatar`（恢复默认）、`GET /avatars/{filename}`（**匿名**，白名单限定 `avatar/` 前缀） |
| 后端模型 / Schema（头像） | `UserOut / MeOut` 增加只读字段 `avatar_url`；`User.avatar_key` 只存对象键 |
| 新增依赖与资源 | `api/requirements.txt` 增加 `pillow`（解码 / 裁切缩放 / 重编码）；仓库内置默认头像 `api/app/assets/avatar-default.png` |
| 前端（管理页） | `Users.vue`：列表加 3 列，新增/编辑弹窗加 3 项（显示名称必填、默认用户名）；操作列新增「重置密码」弹窗（单字段） |
| 前端（管理页改密入口调整） | 编辑弹窗不再放密码框（仅新增时填写建号密码），改密统一走「重置密码」 |
| 前端（用户自己） | `MainLayout.vue` 顶栏显示显示名称；下拉菜单加「个人资料」「修改密码」；新增 `ProfileDialog.vue`、`ChangePasswordDialog.vue` |
| 前端（状态 / API 层） | `stores/user.ts` 扩展 `UserInfo` 与 `displayName` getter，新增 `updateProfile / changePassword`；`api/system.ts` 增加 `updateProfile / changePassword / resetPassword` |
| 前端（头像） | 顶栏 `el-avatar`、个人资料弹窗的上传 / 恢复默认、用户管理列表小头像（见 §5.7） |
| 文档 / 测试 | 重新生成 `docs/API接口文档.md`；补后端单测、隔离 E2E 与 `tests/live/` 回归用例 |

## 三、数据模型设计

### 3.1 `users` 表新增列

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `display_name` | `VARCHAR(50)` | 是（见下方说明） | NULL | 显示名称（姓名 / 称呼），业务上必填 |
| `phone` | `VARCHAR(30)` | 是 | NULL | 联系电话 |
| `email` | `VARCHAR(100)` | 是 | NULL | 电子邮箱 |
| `avatar_key` | `VARCHAR(150)` | 是 | NULL | 头像在对象存储中的对象键；为空表示使用默认头像（见 §5.2） |

关于"必填"与可空的取舍：**数据库列保持可空**。理由是 `ALTER TABLE ADD COLUMN` 加非空列必须带默认值，会给存量库引入一个需要长期维护的默认值；改为"列可空 + 迁移回填 + 接口层必填"三重保障，既不锁死历史行，也保证新写入的数据一定非空。

`avatar_key` 同样保持可空：头像不是必填资料，未设置时接口统一输出默认头像 URL，前端无需处理"没有头像"的分支。

命名与长度对齐仓库既有习惯：`employee`、`customer` 等表的 `name/phone/email` 采用相同长度档位（姓名 50、电话 30、邮箱 100）。

### 3.2 存量库迁移与回填

`api/app/core/database.py` 的 `init_db()` 用 `Base.metadata.create_all` 只会**补建缺失的表，不会给已有表加列**；仓库已有的兜底做法是 `_COLUMN_MIGRATIONS` 元组，在启动时做 `ALTER TABLE ... ADD COLUMN`。本次新增四条：

```python
("users", "display_name", "VARCHAR(50)"),
("users", "phone", "VARCHAR(30)"),
("users", "email", "VARCHAR(100)"),
("users", "avatar_key", "VARCHAR(150)"),
```

紧接着执行一次幂等回填（同样在启动时执行，重复跑无副作用）：

```sql
UPDATE users SET display_name = username
WHERE display_name IS NULL OR TRIM(display_name) = '';
```

- 与列迁移同放在 `init_db()` 的同步迁移流程里（新增一个数据修复步骤，或复用同一个 `run_sync` 回调），保证"部署即生效"，无需人工 SQL。
- 语句用通用 `VARCHAR` / `TRIM`，Postgres（生产 `demo-db`）与 SQLite（单测）均兼容。
- 回填后，存量账号的显示名称即等于用户名，与"管理员建号默认取用户名"的规则一致。
- 前端仍保留"显示名称为空时回退用户名"的展示规则（§6.2），作为直接改库或异常数据时的兜底。

### 3.3 与 `employee_id` 的关系（本期不动）

`User` 已有 `employee_id` 外键，但用户管理页未暴露。可选方案是"用户资料从员工档案带出"，但会引入"没有员工档案的账号（如纯管理 / 对接账号）就填不了资料"的退化，且需要额外的员工选择控件与联动逻辑。因此本期选择**在 `users` 上直接存这三个资料字段**（`avatar_key` 同理，见 §5.2），互不依赖；后续若要做"从员工档案导入"，可作为一次性填充动作叠加，不影响本次表结构。

## 四、后端接口设计

### 4.1 管理侧（`api/app/api/routes/system.py`，权限不变）

| 接口 | 变更 | 权限 |
| --- | --- | --- |
| `POST /api/users` | 请求体新增 `display_name / phone / email`；`display_name` 省略时**服务端默认取 `username`** | `system:user:manage` |
| `PUT /api/users/{user_id}` | 请求体新增同上三项；传入 `display_name` 时必须非空 | `system:user:manage` |
| `GET /api/users` | 响应项新增三项 | `system:user:view` |
| `GET /api/users/{user_id}` | 响应新增三项 | `system:user:view` |

`UserOut` 扩展后（增量字段，老前端忽略新字段不受影响）：

```json
{
  "id": 3,
  "username": "saler01",
  "display_name": "王小明",
  "phone": "13800001234",
  "email": "wangxm@example.com",
  "avatar_url": "/api/avatars/u3-8f3c9d1e4b7a4c2f9e0d5b6a7c8d9e0f.png",
  "employee_id": null,
  "is_active": true,
  "created_at": "2026-10-12T10:00:00",
  "roles": [{"id": 2, "name": "销售员"}]
}
```

两点补充：

- 列表关键词筛选从"仅 `username`"扩展为"`username` 或 `display_name`"，便于按姓名找账号。
- "必填"由三层保证：前端表单必填、服务端创建时缺省取用户名、更新时禁止置空。**不额外增加兼容负担**：`POST /users` 省略 `display_name` 仍返回 201（默认取用户名），因此既有 API 调用方与单测无需改动。

### 4.2 自助资料（新增，`api/app/api/routes/auth.py`）

```
PUT /api/auth/me
Authorization: Bearer <token>     # 仅要求已登录，不要求 system:user:manage

Request:  { "display_name": "王小明", "phone": "13800001234", "email": "wangxm@example.com" }
Response: MeOut（与 GET /auth/me 同结构，含更新后的三个字段）
```

设计要点：

1. **权限**：只挂 `CurrentUser`，不加 `require_permission(...)`。这是必须的——普通业务账号没有 `system:user:manage`，若复用 `PUT /users/{id}` 会让"用户维护自己资料"直接 403。
2. **可改范围**：`display_name / phone / email`，即除用户名外的全部资料字段。
3. **只作用于本人**：不接受 `user_id`；不接受 `username / password / is_active / employee_id / roles`（未知字段按 Pydantic 默认忽略，不产生副作用）。
4. **部分更新语义**：字段未传 = 不变；`phone / email` 传 `""` 或 `null` = 清空；`display_name` 传空 = 400（必填，不允许清空）。
5. **去空格**：写入前 `strip()`，全空白按上面规则处理。
6. **审计**：写一条审计日志，`module="auth"`、`action="update"`、`detail="更新个人资料：<变更字段名列表>"`，落在既有「操作日志」页。
7. **不含头像**：头像是二进制文件，走 multipart 专用接口 `PUT /auth/me/avatar`（见 §5.3），本接口只处理 JSON 文本字段。

### 4.3 自助改密（新增，`api/app/api/routes/auth.py`）

```
PUT /api/auth/me/password
Authorization: Bearer <token>     # 仅要求已登录

Request:
{
  "old_password":    "admin123",        # 必填：原密码
  "new_password":    "newpass1234",     # 必填：新密码（6–100 位）
  "confirm_password":"newpass1234"      # 必填：新密码二次确认，必须与 new_password 一致
}
Response: { "message": "密码已修改" }
```

校验与行为矩阵（自上而下执行，命中即返回，不落库）：

| 检查 | 失败结果 | 说明 |
| --- | --- | --- |
| 三个字段是否齐全 / 长度是否在 6–100 | 422 | 由 Pydantic `Field` 约束统一返回 |
| 两次新密码是否一致 | 400「两次输入的新密码不一致」 | 服务端必须复核，不能只靠前端 |
| 原密码是否正确 | 400「原密码不正确」 | 复用 `core/security.verify_password` |
| 新密码是否与原密码相同 | 400「新密码不能与原密码相同」 | 避免无意义改动与审计噪音 |
| 全部通过 | 200，写库 + 审计 | 用 `hash_password`（PBKDF2-SHA256 / 120k 次迭代，与建号同一函数）重新哈希 |

补充说明：

- **审计日志**：`module="auth"`、`action="update"`、`detail="修改登录密码"`。**绝不写入任何密码、哈希或长度片段**，只记录事件本身（IP 等字段沿用现有 `AuditLog` 能力，与 `login` 日志风格保持一致）。
- **令牌**：JWT 无状态，改密不会自动吊销既有令牌（见 §八 风险与可选加固）。
- **不暴露**：接口不回显密码哈希，`MeOut` 中也不含任何密码字段。

### 4.4 管理员重置密码（新增，`api/app/api/routes/system.py`）

```
POST /api/users/{user_id}/reset-password
Authorization: Bearer <token>     # 需要 system:user:manage

Request:  { "new_password": "newpass1234" }     # 单字段，6–100 位
Response: { "message": "密码已重置" }
```

设计要点：

1. **权限**：复用现有 `MANAGE_USERS` 依赖（`system:user:manage`），不新增权限编码。
2. **按要求刻意省略**原密码校验与二次确认：管理员重置等价于"账号接管"能力，因此必须落在有管理权限的角色上，并强制审计（§七）。相比之下，用户自助改密保留"验原密码 + 二次确认"，两者边界清晰。
3. **单字段 `new_password`**：请求体不引入 `confirm_password`；前端也只放一个输入框。
4. **不做"新密码与原密码相同"的校验**：本接口不读取原密码，无法也无需比较。
5. **允许重置任意账号**（含管理员自己、含最后一个可用管理员）：重置不改变启用状态，因此不触发"系统需保留至少一个可用管理员"约束；管理员想改自己密码时走这个入口同样合规。
6. **审计**：`module="system"`、`action="reset_password"`、`detail="重置用户 {username} 的登录密码"`。使用独立 action，便于在「操作日志」里单独筛选；**不含密码明文与哈希**。
7. **与既有 `PUT /users/{id}` 的关系**：该接口原有的 `password` 字段**保留**（兼容外部 API 调用方与既有单测，语义同样是"不校验原密码的重置"）；前端不再使用它，统一走本接口，避免"只想改资料却顺手改了密码"。

### 4.5 字段校验规则（管理侧与自助侧共用）

| 字段 | 规则 | 违反时 |
| --- | --- | --- |
| `display_name` | 业务必填；`strip()` 后 1–50 字符；创建时省略则默认取 `username` | 422（超长）/ 400（显式传空） |
| `phone` | 可选；允许数字、`+`、空格、括号、`-`，3–30 字符 | 422 |
| `email` | 可选；轻量格式校验（`^[^@\s]+@[^@\s]+\.[^@\s]+$`），≤100 字符 | 422 |
| `new_password` | 必填；6–100 字符（与建号密码同档） | 422 |
| `confirm_password` | 必填；必须等于 `new_password` | 400 |

刻意不引入 `email-validator` / `pydantic[email]`：`api/requirements.txt` 目前没有该依赖，而本期只需要"别把明显写错的东西存进去"，轻量正则即可（自建部署、无外网注册流程）。

`new_password` 在校验规则上与"自助改密"共用长度约束；`confirm_password` 仅自助改密接口使用，管理员重置接口不接收该字段。

### 4.6 自助范围边界（明确写死，避免歧义）

| 字段 | 自助可改 | 原因 |
| --- | --- | --- |
| `display_name` / `phone` / `email` | 是 | 就是"个人资料"本身 |
| 头像 | 是（走专用 multipart 接口，见 §5.3） | 属于"个人资料"，但传输形态与 JSON 不同，单独成接口 |
| 密码 | 是（走专用接口，需验原密码） | 本次新增需求 |
| `username` | 否 | 登录凭据与审计主体标识，改名会影响历史日志可读性 |
| `is_active` | 否 | 允许自助停用等于自锁账号，且与"系统需保留至少一个可用管理员"约束冲突 |
| 角色 / 权限 | 否 | 自助提权是典型越权，必须走管理员分配 |
| `employee_id` | 否 | 属于组织归属信息，由管理员维护 |

## 五、头像设计（上传 / 规范化 / 匿名读取）

### 5.1 总体思路

1. 头像文件一律存**对象存储**（沿用 `api/app/core/storage.py` 的 MinIO 封装），不落数据库、也不落应用容器本地磁盘（容器重启即丢，多副本也不共享）。
2. 数据库只存**对象键**（`users.avatar_key`），接口对外只暴露 `avatar_url`，前端不关心 key 规则。
3. **上传的原始字节不会被直接当作头像存回去**：统一"解码 → 居中裁切缩放为 256×256 → 重新编码为 PNG"后再上传。这一条同时解决了四个问题：
   - 存储里永远只有真实 PNG，杜绝"改名的 HTML / SVG / polyglot 文件被当作图片回吐"；
   - EXIF（含 GPS 定位）等元数据被丢弃；
   - "256×256"成为**产出规格**，用户上传任意比例（竖图、横图、非正方形）都能得到合规头像；
   - 单张体积可控（实测 256×256 PNG 约 20–100KB），存储与带宽成本可预期。
4. 读取接口**匿名开放**（浏览器 `<img>` 带不上 `Authorization` 头），但用**白名单正则**把可读范围死死限定在头像 key 上。绝不能做成"传什么 key 就取什么对象"——否则 S3 里 `gsp/certificates/...` 的证照扫描件会被绕过权限直接下载（这一条同时写进 §七 与 §八）。

### 5.2 数据与存储布局

数据库侧只加一列 `users.avatar_key`（§3.1），对外表现为 `avatar_url`：

| 情形 | `avatar_key` | `avatar_url` |
| --- | --- | --- |
| 未设置头像（含全部存量用户、新建用户） | NULL | `/api/avatars/default.png` |
| 已设置头像 | `avatar/u{user_id}-{uuid4_hex}.png` | `/api/avatars/{该文件名}` |

对象键规则（单段文件名，便于路由匹配与白名单校验）：

- 默认头像：`avatar/default.png`（启动时幂等写入，见 §5.6）
- 用户头像：`avatar/u{user_id}-{uuid4().hex}.png`，例如 `avatar/u42-8f3c...（32 位十六进制）.png`

**为什么用随机文件名，而不是固定的 `avatar/{user_id}.png`：**

- 随机 key 天然充当"缓存版本号"——换头像即换 URL，浏览器 / CDN 不需要靠 `no-cache` 或查询参数猜缓存；
- 换头像与恢复默认时**尽力删除旧对象**（失败仅记告警，不阻塞请求），即使删除失败，残留的也只是一个不可达的孤儿对象，不会造成越权读取（新的 URL 已经指向新 key）。

### 5.3 上传 / 删除接口（自助）

```
PUT /api/auth/me/avatar            Content-Type: multipart/form-data，字段名 file
Authorization: Bearer <token>      # 仅要求已登录，不要求 system:user:manage

Response: MeOut（含更新后的 avatar_url）
```

行为：校验（§5.5）→ 规范化 → 上传新 key → 写 `avatar_key` → 尽力删除旧 key → 写审计 → 返回 `MeOut`。

```
DELETE /api/auth/me/avatar
Authorization: Bearer <token>

Response: MeOut（avatar_key 置空，avatar_url 回落默认头像）
```

行为：清空 `avatar_key` → 尽力删除旧对象 → 写审计。用于「恢复默认头像」。

设计要点：

1. **放在 `/auth/me/**` 而不是 `/users/{id}/avatar`**：与自助改资料、自助改密同构——只用 `CurrentUser`，普通业务账号也能改自己的头像。管理员替他人设置头像不在本期范围（§十一）。
2. 上传 / 删除失败时给出可读中文错误：对象存储不可用 → 503「对象存储不可用」；校验不通过 → 400/413（§5.5）。
3. 数据库写库与对象上传的顺序：**先传对象、后写库**，写库成功后再删旧对象。即使写库失败，最坏结果是多一个孤儿对象（不可达），不会出现"库里指向一个不存在的 key"。
4. 审计：`module="auth"`、`action="update"`、`detail="更新头像"` / `"恢复默认头像"`；**不记录文件名与对象键**（避免把内部存储结构写进日志）。

### 5.4 匿名读取接口

```
GET /api/avatars/{filename}        # 无需认证
```

- **白名单正则**：`^(default\.png|u[0-9]{1,9}-[0-9a-f]{32}\.png)$`。不匹配一律返回 **404**（而不是 403——避免通过错误码区分"不存在"与"无权限"，从而泄露 key 空间）。
- 前缀固定：命中后只读 `avatar/` 前缀下的对象（`storage.get_object(f"avatar/{filename}")`），**永远不允许调用方影响前缀**。这条是匿名接口的安全边界：`gsp/certificates/...` 之类的 key 既进不了正则、也不在允许前缀内。
- **不做 302 跳转到 presigned URL**：签名地址指向 `http://medsales-minio:9000`（容器内网主机名），浏览器根本访问不到；因此由 API 取回字节流式回传。
- 响应头：
  - `Content-Type: image/png`（存储里只有规范化后的 PNG，不依赖对象元数据，避免"用上传者声明的类型回吐"）；
  - `Cache-Control: public, max-age=604800, immutable`（随机文件名保证内容不可变）；
  - `ETag`（对象内容摘要）+ 支持 `If-None-Match` → `304`，减少重复传输；
  - `X-Content-Type-Options: nosniff`（与证照预览保持一致的加固习惯）。
- 对象缺失（默认头像尚未初始化、或指向已删除的孤儿 key）→ 404；对 `default.png` 额外做一次"懒初始化"兜底（确保默认头像存在后再取，见 §5.6）。
- 匿名端点**不写审计日志**：每次页面渲染都会请求头像，写日志只会淹没真正的操作记录。
- 无需 CORS 配置：`<img>` 加载图片不受同源策略限制，浏览器不会为它发预检请求。

### 5.5 图片校验与规范化

| 检查 | 规则 | 失败返回 |
| --- | --- | --- |
| 文件大小 | ≤ 1MB（分块读取累计，超限立即中止，不把超限内容读进内存） | 413「头像文件过大（上限 1MB）」 |
| 允许格式 | jpg / jpeg / png / bmp / webp / gif，**以实际解码结果为准**（扩展名只用于快速拒绝） | 400「不支持的图片格式」 |
| 真实解码 | `Image.open()` + `verify()`；解码失败（如 txt 改名 `.png`） | 400「不是有效的图片文件」 |
| 像素规模 | 防解压炸弹：`Image.MAX_IMAGE_PIXELS` 上限 + 单边 ≤ 10000px | 400「图片分辨率过大」 |
| 规范化 | 居中裁切（cover）→ 缩放 → 256×256；GIF 取首帧；保留透明通道（RGBA）；重新编码 PNG | — |

补充说明：

- **"256×256"是产出规格而不是上传门槛**：上传任意尺寸（含非正方形）都会被规范化，这是更友好的行为；若希望"非 256×256 一律拒绝"，把这一步从"裁切缩放"换成"尺寸校验 + 400"即可（见 §十一）。
- **GIF 只取首帧**：动图头像不支持，落库为静态 PNG。
- 前端会做同样的白名单 + 1MB 预校验（提前反馈、省流量），但**服务端是唯一权威**——前端校验只是体验优化。
- 新增依赖 `pillow`：写入 `api/requirements.txt`（`api/Dockerfile` 本来就按 requirements 安装，无需改动 Dockerfile）；宿主机 venv 与容器都要装。官方 wheel 默认包含 WebP 支持（`Image.open` 直接可读 webp）。

### 5.6 默认头像初始化

- 仓库内置一张 256×256 的 PNG：`api/app/assets/avatar-default.png`（`api/Dockerfile` 的 `COPY app ./app` 会一并打包进镜像）。
- 启动时（`api/app/main.py` 的 lifespan，紧跟 `storage.ensure_bucket()`）调用 `ensure_default_avatar()`：`head_object("avatar/default.png")` 不存在则 `put_object`。**幂等**（每次启动只做一次 head 检查）、失败仅记告警、绝不阻塞应用启动（与 `ensure_bucket` 的容错策略一致）。
- 存储不可用导致默认头像取不到时：匿名接口 404，前端 `el-avatar` 用 `icon` 插槽兜底显示占位图标，页面不会空白或报错。
- 需要换默认头像风格时，只替换这张 PNG 即可（下次启动覆盖写入）。

### 5.7 前端接入

| 位置 | 内容 |
| --- | --- |
| 顶栏（`MainLayout.vue`） | 右上角 `el-avatar :size="32"` + 显示名称；下拉菜单顶部也带一张小头像 |
| 个人资料弹窗（`ProfileDialog.vue`） | 头像区：`el-avatar :size="72"` 预览 + 「上传头像」（隐藏 `input[type=file]`）+「恢复默认」两个按钮 |

| 个人资料 / 密码弹窗 | 不含头像字段（头像走独立上传流程，与 §6.3 的表单互不干扰） |

- 上传流程：选择文件 → 客户端校验（格式白名单 / ≤1MB）→ 本地预览（`URL.createObjectURL`）→ 调用 `PUT /auth/me/avatar` → `userStore.fetchMe()` 刷新顶栏头像。

- URL 拼接：复用 `frontend/src/utils/request.ts` 已导出的 `baseURL`（`${baseURL}/avatars/${filename}`），不硬编码域名；生产环境 `baseURL = /api`，与 nginx 同源反代天然契合。
- `data-test`：`header-avatar`、`avatar-preview`、`avatar-upload`、`avatar-remove`。

### 5.8 部署与缓存注意

- 前端 nginx 已有 `client_max_body_size 25m`，1MB 的头像不会在网关层被拦；**无需改 nginx**。
- `frontend/src/utils/request.ts` 的 413 分支目前写死"单文件上限 20MB"文案，接入头像后会出现"1MB 超限却提示 20MB"的误导。本次把该文案改为中性表述（"文件过大，超出服务器允许的上传体积"），具体上限由各上传入口（证照 20MB / 头像 1MB）自己提示。
- MinIO 数据卷（`medsales-minio-data`）已持久化，头像与证照共用一个 bucket，靠前缀隔离（`avatar/` 与 `gsp/`）。**匿名读取的白名单只放行 `avatar/` 前缀**，这是本设计的硬约束，单测必须覆盖。
- 头像属于"可再生成"的展示资源，不纳入业务数据备份口径（数据库只存 key，丢失后自动回落默认头像）。

## 七、权限、审计与安全

| 场景 | 谁能做 | 依赖 |
| --- | --- | --- |
| 查看用户列表 / 详情（含新字段） | 拥有 `system:user:view` 的账号 | 现有权限 |
| 新增用户并填写资料、编辑他人资料 | 拥有 `system:user:manage` 的账号 | 现有权限 |
| 维护自己的显示名称 / 电话 / 邮箱 | 任何登录账号 | 仅需有效 JWT，不新增权限编码 |
| 修改自己的登录密码 | 任何登录账号（须提供原密码） | 仅需有效 JWT，不新增权限编码 |
| 上传 / 删除自己的头像 | 任何登录账号 | 仅需有效 JWT，不新增权限编码 |
| 匿名读取头像 | 任何人（无需令牌、无需权限） | 白名单正则 + 固定 `avatar/` 前缀（§5.4） |
| 重置任意账号的登录密码（含他人） | 拥有 `system:user:manage` 的账号 | 现有权限；不校验原密码，强制审计 |

- 不新增权限编码，`sync_permission_catalog` 与「权限管理」页目录无需变更。
- 审计日志（统一落在既有「操作日志」页，可按 `module` 过滤 `auth`）：

| 事件 | module | action | detail |
| --- | --- | --- | --- |
| 自助改资料 | `auth` | `update` | `更新个人资料：显示名称、电话`（仅列变更字段，不写值） |
| 自助改密码 | `auth` | `update` | `修改登录密码`（不含任何密码信息） |
| 自助改头像 / 恢复默认 | `auth` | `update` | `更新头像` / `恢复默认头像`（不记录文件名与对象键） |
| 管理员重置密码 | `system` | `reset_password` | `重置用户 xxx 的登录密码`（不含任何密码信息） |
| 管理员建号 / 改用户资料 | `system` | `create` / `update` | 沿用现有 `_audit()` 实现，字段名天然覆盖新字段 |

- 越权防护：两个自助接口都只作用于 `CurrentUser`，不接受目标用户 ID；`username / is_active / 角色 / employee_id` 均不在可写字段内。
- 管理员重置密码是"无原密码校验"的账号接管能力，因此**只**通过 `system:user:manage` 开放，且必须在同一次事务里落审计日志（单测覆盖无权限调用返回 403）。
- 密码仅以哈希形式存在（`hash_password`，PBKDF2-SHA256 / 120k 迭代），接口与日志均不回显。
- 匿名头像接口的安全边界只有两条，必须同时成立：**白名单正则**（只认 `default.png` 与 `u{digits}-{32 位十六进制}.png`）+ **固定 `avatar/` 前缀**。任何一条被放宽，`gsp/` 下的证照扫描件就可能被匿名下载，因此单测把"用非头像 key 调该接口必须 404"列为必测项。
- 图片处理在服务端完成，且**只回吐重新编码后的 PNG**：不信任上传者的 content-type、不信任扩展名、不把原始字节直接存回对象存储。

## 八、兼容性与风险

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| 存量库缺列导致 500 | `create_all` 不会给已有表加列 | `_COLUMN_MIGRATIONS` 四条 ALTER + 幂等回填，随容器重启生效 |
| 历史数据资料为空 | 资料列为 NULL、`avatar_key` 为 NULL | 启动回填 `display_name = username`；顶栏保留"为空回退用户名"；列表空值显示 `-`；头像回落到默认头像 |
| 破坏既有 E2E | `auth.spec.ts` 断言顶栏文本是 `admin`；`test_system.spec.ts` 走"用户名 / 密码"两字段建号 | 回填 + 服务端默认取用户名，既有用例不改也能通过 |
| 改密后旧令牌仍有效 | JWT 无状态，改密不吊销其它已签发令牌 | 本期接受并写入文档；若需要"改密踢下线"，后续引入 `token_version` 声明（记为可选加固） |
| 管理员重置密码无原密码校验 | 越权调用等同于接管他人账号 | 仅在 `system:user:manage` 下开放；强制独立审计 action；前端仅对有权账号展示按钮，后端独立校验（不依赖前端隐藏） |
| 匿名头像接口被当成"任意对象下载器" | 一旦允许任意 key，可绕过权限拿到 `gsp/` 证照扫描件 | 白名单正则 + 固定前缀；不匹配即 404；单测覆盖（§九） |
| 上传图片作为攻击载荷 | 伪造扩展名、polyglot、解压炸弹 | 实际解码校验 + 重新编码 PNG + 像素上限 + ≤1MB |
| 新增依赖 Pillow | 镜像体积略增；构建阶段需联网安装 | 写入 `requirements.txt` 并固定版本；构建阶段本就联网（Dockerfile 无需改动） |
| 旧头像对象残留 | 换头像 / 恢复默认后旧对象未删除成功 | 尽力删除 + 失败仅告警；随机 key 让残留对象不可达，不影响功能与安全 |
| GIF 动图降级为静态图 | 动图只保留首帧 | 明确为设计取舍并写入文档（§十一），如需动图需另立需求 |
| 头像显示依赖对象存储可用性 | 存储不可用时头像 404 | 前端 `el-avatar` 占位兜底，页面不报错；业务功能不受影响 |
| 原密码可被暴力尝试 | 自助改密接口目前无限流 | 本期不做；现有登录接口同样未限流，可在后续统一加限流（记为已知项） |
| 响应体字段新增 | 前端 `UserRow` / `UserInfo` 类型需同步 | 类型定义同步扩展；未更新的消费方忽略新字段 |
| 显示名称不可清空 | "必填"与"允许清空"互斥 | 接口层对显式空值返回 400，前端必填校验兜住 |
| 邮箱不唯一 / 不校验真实性 | 系统未基于邮箱登录或找回密码 | 明确列为非目标；若后续要唯一约束，需单独处理历史重复数据 |

### 12.4 实施中的偏差与经验

1. **资料字段不能走 `update_and_commit`**：该公共 helper 把 `None` 视为"未修改"（`if value is not None`），而资料字段需要"显式传空 = 清空"。因此 `update_user` 里把 `display_name / phone / email` 单独 `setattr`，其余字段仍走 helper（保持既有语义不变，`employee_id` 等行为零变化）。
2. **`avatar_url` 用模型属性派生**：`User.avatar_url` 由 `avatar_key` 计算（为空回落默认头像），配合 `UserOut` 的 `from_attributes` 直接序列化，避免在每处路由手写拼接。
3. **E2E 不要用"可见的成功提示"判断动作完成**：Element Plus 的 toast 有约 3 秒存活期，前一步的成功提示会让后一步的断言"假通过"，进而在写入尚未落库时就去查库（首次实现管理员重置密码用例时踩到，表现为"旧密码仍然可登录"）。现在统一改为 `waitForResponse` + 断言弹窗关闭。
4. **`.png` 之外的非白名单扩展名在服务端与前端都被拦**：前端用 `accept` + MIME 预校验，服务端以"实际解码结果"为准，两者互补。
5. **保留 `PUT /users/{id}` 的 `password` 字段**：外部 API 调用方与既有单测仍在使用，语义与新的重置接口一致；前端已不再走这条路径。
