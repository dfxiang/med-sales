## 三、缺陷详情

### BUG-01 库存列表分页 `total` 返回当前页行数

- **位置**：`api/app/api/routes/inventory.py` → `list_inventory`，结尾 `return page_of(result, len(result), params.page, params.size)`
- **现象**：`total` 被赋值为 `len(result)`（当前页实际返回行数），而非数据库真实总数。
- **实测证据**（`GET /api/inventory`）：

  | 请求 | 返回 `total` | 返回行数 | 数据库真实行数 |
  | --- | --- | --- | --- |
  | 默认 (`size=20`) | 20 | 20 | 3240 |
  | `page=1&size=5` | 5 | 5 | 3240 |
  | `page=1&size=100` | 100 | 100 | 3240 |

- **影响**：前端分页器永远只显示 1 页（`total == size`），用户最多只能看到前 20 条库存，其余 3220 条无法访问。
- **根因**：分页函数已正确返回 `(rows, total)`，但返回时丢弃了真实 `total`。

### BUG-02 库存列表 `status` 过滤在分页之后执行

- **位置**：`api/app/api/routes/inventory.py` → `list_inventory`，`if status and s != status: continue` 位于分页取数之后。
- **现象**：`status` 条件只作用于“当前页已取出的若干行”，而非全表。
- **实测证据**：

  | 请求 | 返回 |
  | --- | --- |
  | `GET /api/inventory?status=库存不足&size=5` | `total=0, items=[]` |
  | `GET /api/inventory?status=库存预警&size=5` | `total=0, items=[]` |
  | `GET /api/inventory?status=库存充足&size=5` | `total=5, items=[库存充足×5]` |

- **影响**：按状态查询库存不可用（结果错误或为空）；即使按状态筛出结果，`total`/页码也不可信。
- **根因**：`stock_status` 为 Python 侧计算值，未下推到 SQL，导致无法在数据库层过滤与计数。

### BUG-03 库存状态报表硬编码 `size=200`，静默截断

- **位置**：`api/app/api/routes/reports.py` → `inventory_status`，`list_inventory(db, PageParams(page=1, size=200), ...)`
- **现象**：报表接口只能返回前 200 条库存，超出部分无任何提示。
- **实测证据**：`GET /api/reports/inventory-status` 恒返回 200 条，而数据库库存为 3240 条。
- **影响**：报表数据不完整，且用户无法翻页获取剩余数据，属于静默数据丢失。

### BUG-04 应收账龄接口无分页且为 N+1 查询

- **位置**：`api/app/api/routes/finance.py` → `list_receivables`
- **现象**：接口遍历**全部**销售订单（211772 条），对每条未收讫订单单独 `db.get(Customer, ...)`，最后一次性返回全部结果。
- **实测证据**：
  - `GET /api/receivables` → `HTTP 200`，耗时 **36.88s**，返回 **5228** 行，响应体 ~1.37MB。
  - 传 `page`/`size` 参数无效（接口未声明），返回行数不变。
- **影响**：页面加载极慢甚至超时；数据量继续增长后会直接不可用。
- **根因**：缺少 SQL 层过滤/分页 + 逐行查询客户（N+1）。

### BUG-05 客户/销售员/商品销售汇总接口无分页

- **位置**：`api/app/api/routes/reports.py` → `customer_summary` / `employee_summary` / `product_summary`
- **现象**：三个接口均返回 `list[...]`，不接受 `page`/`size`，全量返回。
- **实测证据**：`customer-summary` 1650 行 / 565KB、`employee-summary` 500 行、`product-summary` 365 行（耗时 4.1s），传分页参数无效。
- **影响**：页面一次性加载并渲染全部行；数据增长后前端卡顿、接口变慢。

### BUG-06 每日/月度销售汇总接口无分页

- **位置**：`api/app/api/routes/reports.py` → `sales_daily` / `sales_monthly`
- **实测证据**：`sales-daily` 返回 1673 行（321KB），`sales-monthly` 返回 55 行，均不接受分页参数。
- **说明**：两接口同时服务于图表与表格，需在保留图表所需数据的前提下为表格加分页。

### BUG-07 证照/批次近效期接口无分页

- **位置**：`api/app/api/routes/gsp.py` → `expiring_certificates` / `expiring_batches`
- **现象**：两接口返回 `list[...]`，不接受分页参数，全量返回（批次数据随业务增长会显著变大）。

### BUG-08 前端报表页面无分页控件

- **位置**：以下 6 个页面直接一次性加载全量数据，页面上无分页控件：
  - `frontend/src/views/CustomerSummary.vue`
  - `frontend/src/views/EmployeeSummary.vue`
  - `frontend/src/views/ProductSummary.vue`
  - `frontend/src/views/InventoryStatus.vue`
  - `frontend/src/views/Receivables.vue`
  - `frontend/src/views/SalesReports.vue`（每日/月度表格）
- **对照**：使用 `CrudPage` 组件的页面，以及 `AuditLogs/Inventory/Movements/OrderDetail/Payments/PriceHistory/PurchaseOrders/Returns/Roles/SalesOrders/Users` 等自定义页面**已有**分页器，问题集中在上述报表类页面。

### BUG-09 非法分页参数返回 HTTP 500

- **位置**：`api/app/api/deps.py` → `get_page_params`（`page: int = 1, size: int = 20`，无 `Query` 约束），随后手工构造 `PageParams`。
- **现象**：超出 `PageParams` 约束（`page≥1`、`1≤size≤200`）时，Pydantic 在校验阶段抛 `ValidationError`，FastAPI 未转为 422，直接 500。
- **实测证据**：

  | 请求 | 期望 | 实际 |
  | --- | --- | --- |
  | `?page=0&size=20` | 422 | **500** |
  | `?page=1&size=0` | 422 | **500** |
  | `?page=1&size=500` | 422 | **500** |
  | `?page=-1&size=20` | 422 | **500** |
  | `?page=abc&size=20` | 422 | 422（该分支正常） |

- **根因**：分页参数未作为 FastAPI 查询参数声明约束，校验被推迟到依赖函数内部。

### BUG-10 全新构建的 API 镜像缺少 greenlet，容器启动崩溃

- **位置**：`api/requirements.txt`（`sqlalchemy>=2.0`）
- **现象**：在本机执行 `docker compose up -d --build` 重新构建后，`medsales-api` 容器反复重启，日志报
  `ImportError: The SQLAlchemy asyncio module requires that the Python 'greenlet' library is installed`。
- **根因**：`sqlalchemy` 的 `asyncio` 扩展依赖 `greenlet`；未使用 `sqlalchemy[asyncio]` 安装目标，
  依赖解析在新版本下不再自动带入 `greenlet`，导致**干净构建**产物无法运行（旧镜像因历史构建偶然包含该库才能启动）。
- **修复**：依赖声明改为 `sqlalchemy[asyncio]>=2.0`。

### BUG-11 库存状态报表「分类」列恒为空

- **位置**：`api/app/api/routes/reports.py` 的 `inventory-status`，其返回结构 `InventoryOut` 缺少 `category_name`。
- **现象**：前端 `InventoryStatus.vue` 有「分类」列，但始终空白。
- **修复**：`InventoryOut` 增加 `category_name` 字段，并在 `list_inventory` 中按商品带出分类名称。

### BUG-12 商品销售汇总把「已取消」订单明细计入销量/销售额

- **位置**：`api/app/api/routes/reports.py` → `product_summary`
- **现象**：`sold_quantity`、`sales_amount` 使用不区分订单状态的 `sum(SalesOrderItem.*)`，
  而已取消订单的明细仍留在 `LEFT JOIN` 结果中，导致销量/销售额虚高；同一查询里的 `order_count`
  却已按未取消统计，口径自相矛盾。
- **实测证据**：

  | 口径 | 金额 |
  | --- | --- |
  | 修复前 product-summary 合计销售额 | 244,885,656,450.86（= 明细表全部，含已取消） |
  | 非取消订单明细合计（正确值） | 233,078,125,210.13 |
  | 客户汇总合计（正确值） | 233,063,085,553.94 |

- **修复**：改用 `func.sum(...).filter(SalesOrder.id.isnot(None))` 仅统计未取消订单明细，
  与其他汇总口径统一。修复后 product-summary 合计 = 233,078,125,210.13，与数据库一致。

### BUG-13 大附件上传被 nginx 以 413 拦截

- **位置**：`frontend/nginx.conf`（未设置 `client_max_body_size`）
- **现象**：证照扫描件上传时，PDF 能成功、手机拍摄的 JPG 一律失败，前端只提示「请求失败，请稍后重试」。
- **实测证据**（同一次排查，三个对照）：

  | 请求 | 结果 |
  | --- | --- |
  | 500KB jpg，经 nginx `:8088` | ✅ 201 |
  | 2MB jpg，经 nginx `:8088` | ❌ **413 Request Entity Too Large**（返回 HTML） |
  | 同一个 2MB jpg，直连后端 `:8001` | ✅ 201 |

- **根因**：nginx 的 `client_max_body_size` 默认为 **1MB**，而 `nginx.conf` 未覆盖该项。超过 1MB 的请求体在网关层即被拒绝，根本到不了 API（后端上限本是 20MB）。PDF 之所以「成功」是因为体积小；文件类型与扩展名后端一直支持。
- **修复**：
  1. `nginx.conf` 增加 `client_max_body_size 25m`（略高于后端 20MB 上限，超限时由后端返回统一中文 JSON 错误）；
  2. 反代增加 `proxy_request_buffering off` 与 `proxy_read_timeout 300s`，避免大文件慢速上传超时；
  3. 前端对 413 单独给出可读提示，并在上传前做大小/类型预检；
  4. live 测试新增「1.5MB 图片经网关上传成功」用例做回归。

## 四、修复原则

1. 所有“服务端列表”统一返回 `Page { items, total, page, size }`，接受 `page`（≥1）与 `size`（1–200）。
2. 过滤条件一律下推 SQL，计数与取数在同一条件集下执行。
3. 前端分页器统一使用 `[10, 20, 50, 100]`、默认 20；筛选/切换条件时回到第 1 页。
4. 每修复一项，均在**本机容器环境**用真实数据回归验证，并回填本清单“状态”列。

## 七、第二轮排查：GSP 合规与对象存储

### 背景

GSP（药品经营质量管理规范）要求对客户/供应商/商品/厂家的资质证照进行归档与到期跟踪，
并保存证照扫描件。本轮排查发现 GSP 模块存在以下问题。

### 缺陷汇总

| 编号 | 模块 | 严重度 | 标题 | 状态 |
| --- | --- | --- | --- | --- |
| BUG-13 | GSP | 高 | 批次管理「商品」下拉框只加载前 200 条，165 个商品无法选择 | 已修复 |
| BUG-14 | GSP | 高 | 证照扫描件无处归档（系统无对象存储），首营资料/合规归档不可用 | 已修复 |
| BUG-15 | GSP | 中 | 证照可关联到不存在的对象，且对象类型无校验，产生孤儿数据 | 已修复 |

### BUG-13 批次管理商品下拉框只加载前 200 条

- **位置**：`frontend/src/views/Batches.vue`（及销售/采购/期初/调价/收付款/订单明细等同类下拉框）
- **现象**：选项加载写法为 `list({ page: 1, size: 200 })`，而列表接口单页上限即 200。
  当商品 365 条时，只能选到前 200 个商品，其余 165 个无法选择；客户下拉框同理（1650 条只加载 200）。
- **实测证据**：部署环境 `GET /api/products?page=1&size=200` → `items=200, total=365`；
  浏览器实测批次「商品」下拉项 = 200（数据库 365）。
- **修复**：新增 `frontend/src/utils/options.ts` 的 `fetchAllOptions()` 自动翻页拉全量，
  并替换批次/商品/销售订单/采购订单/期初建账/调价/收款/退货/用户/角色/库存/订单明细等下拉框的加载方式。
- **验证**：浏览器实测批次「商品」下拉项 = **365**（= 数据库商品总数）。

### BUG-14 证照扫描件无处归档（缺对象存储）

- **现象**：GSP 合规要求归档证照扫描件，但系统此前没有任何文件存储能力，证照只能登记编号/日期，无法上传附件。
- **修复**：
  1. 使用本机 `minio/minio` 镜像部署**本系统专用**的 S3 存储（`medsales-minio`，独立 bucket `medsales`，见 `docker-compose.yml`）。
  2. 后端新增对象存储封装 `api/app/core/storage.py`（boto3，S3v4，path-style），启动时幂等建桶。
  3. 新增 `certificate_attachments` 表与接口：上传/列表/下载/删除（`/api/gsp/certificates/{id}/attachments`、`/api/gsp/attachments/{id}/download` 等）。
  4. 前端证照管理新增「附件」入口（抽屉内上传/下载/删除扫描件）。
- **验证**：上传 PDF → 列表可见 → 下载字节一致（125B）；MinIO 中出现对象
  `gsp/certificates/1/<hex>.pdf`；删除附件后对象同步消失。

### BUG-15 证照关联对象无校验

- **现象**：`POST /api/gsp/certificates` 接受任意 `entity_type` 与 `entity_id`，
  可创建指向不存在对象的证照（`entity_id=999999` 亦返回 201）。
- **修复**：创建证照时校验 `entity_type ∈ {customer,supplier,product,manufacturer}` 且对应对象存在。

## 九、第四轮排查：商品汇总加载极慢（页面看起来像空的）

| 编号 | 模块 | 严重度 | 标题 | 状态 |
| --- | --- | --- | --- | --- |
| BUG-17 | 报表 | 高 | 商品销售汇总接口约 4.7s，页面长时间空白/看似无数据 | 已修复 |

### 现象

打开「商品汇总」页面长时间没有任何内容，疑似空白。实测并非无数据，而是接口 `GET /api/reports/product-summary` 耗时约 **4.7 秒**，且表格没有加载动画，用户误以为页面是空的。翻页/切换每页条数会重新触发一次全量聚合（每翻一页都要再等约 4.7s）。

### 根因（EXPLAIN ANALYZE）

1. `count(DISTINCT so.id)` 让 PostgreSQL 放弃哈希聚合，改为**对约 160 万行销售明细做排序**（`Sort Method: external merge  Disk: 62448kB`），产生约 62MB 磁盘溢写。
2. 排除「已取消」订单时，与约 20 万条销售订单做主表连接；而已取消订单仅约 1 万条。
3. 启用 JIT，额外消耗约 0.28s。

### 修复

1. **反向过滤**：用 `NOT IN (已取消订单)`（哈希 anti-join，哈希表仅约 1 万条）替代与 20 万订单的连接。
2. **拆散去重计数**：把「去重订单数」拆成独立子查询，按 `(product_id, sales_order_id)` 利用 `idx_sales_order_item_product` 索引顺序去重，避免磁盘排序。
3. **结果缓存 60s**：聚合结果按商品仅 365 行，服务端缓存后翻页/切换条数即时返回；**销售订单新增/取消/删除时自动清缓存**，保证数据及时刷新。
4. **前端加载动画**：商品汇总等报表页表格加 `v-loading`，加载期间显示 loading，不再"看起来是空的"。

### 效果

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 接口冷启动（真实聚合） | ~4.7s | **0.53s** |
| 接口缓存命中 / 翻页 | ~4.7s（每次重算） | **~4ms** |
| 前端首屏出现数据 | 页面长时间空白 | **~1.3s**（含页面加载，期间显示 loading） |
| 前端翻页 | ~4.7s | **74ms** |

### 验证

- 数据正确性：全量合计销售额 = `233,078,125,210.13`，与数据库未取消订单明细合计**完全一致**；抽查 `product_id=9`：销量 3506523 / 销售额 4403597690.98 / 订单数 3688，与 SQL 直查一致。
- 缓存失效：新建销售订单后接口重新计算（0.56s），删除后再次重算（0.55s），连续请求命中缓存（4ms）。
- 后端 `pytest` **53/53 通过**；前端 E2E **38/38 通过**。

> 说明：商品汇总结果存在最长 60s 的缓存；销售订单的增删/取消会立即清缓存。如需完全实时（无缓存），可将 `_PRODUCT_SUMMARY_TTL_SECONDS` 设为 0。

## 十二、第七轮排查：权限控制模块

### 背景

系统已有 `users` / `roles` / `permissions` / `role_permissions` 等表与相应 CRUD 接口，
但「权限」此前只是**被存储的数据**，不产生任何约束作用。本轮对照运行环境逐接口实测确认并修复。

### 缺陷汇总

| 编号 | 模块 | 严重度 | 标题 | 状态 |
| --- | --- | --- | --- | --- |
| BUG-20 | 权限 | 严重 | 权限未参与接口校验，任何登录账号（含无任何角色）可读写全部数据，甚至删除内置「全部权限」 | 已修复 |
| BUG-21 | 权限 | 中 | 角色/权限列表的 `keyword` 筛选无效（后端未接收该参数），前端搜索框形同虚设 | 已修复 |
| BUG-22 | 权限 | 中 | 系统管理高危操作缺少保护与留痕：可删除/停用自己、可删除仍被引用的角色与权限 | 已修复 |
| BUG-23 | 前端 | 中 | 前端无权限感知：菜单、路由、按钮对所有账号一视同仁 | 已修复 |

### BUG-20 权限未参与接口校验

- **位置**：`api/app/api/deps.py`（只有 `get_current_user` 认证，无权限判定）、各业务路由（无 `Depends` 权限声明）
- **现象**：`get_current_user` 只校验令牌有效与账号启用，**从不检查角色/权限**；`require_permission` 之类的依赖在代码中根本不存在。
- **实测证据**（建一个不分配任何角色的账号 `probe_noperm` 后，用它的令牌请求）：

  | 请求 | 结果 | 期望 |
  | --- | --- | --- |
  | `GET /api/users` | **200**（返回全部账号列表） | 403 |
  | `GET /api/roles` | **200** | 403 |
  | `GET /api/audit-logs` | **200** | 403 |
  | `DELETE /api/permissions/1`（内置「全部权限」） | **200**（权限被删除） | 403 |

  > 该探测确实删除了内置权限，已立即还原（重建 `all` 权限并重新绑定到「管理员」角色）。
  > 这恰好也说明：低权限账号不仅能读，还能删掉整个权限体系的根基。

- **根因**：权限数据（`permissions` / `role_permissions`）只被「角色权限」页面用于展示与维护，
  从未接入请求处理链路，属于「有模型、无执行」。
- **修复**：
  1. 新增权限内核 `api/app/core/permissions.py`：内置权限目录 `PERMISSION_CATALOG`（34 项，覆盖工作台/系统/组织/客户/商品/供应商/仓库/采购/销售/库存/退货/财务/报表/GSP）、
     通配权限 `all`、判定函数 `has_permission()`，以及幂等补建的 `sync_permission_catalog()`（服务启动时执行）。
  2. `api/app/api/deps.py` 新增依赖工厂 `require_permission(*codes)`（编码不存在时 403，提示所需权限的中文名称）。
  3. 为全部业务路由挂上读/写权限（`*:view` / `*:manage`），共 **103 个接口**；
     `/auth/me` 增加 `permissions` 与 `is_superuser` 字段，供前端做界面收敛。
  4. 新增初始化脚本 `api/scripts/seed_permissions.py`（同步清单，`--with-roles` 可创建销售员/采购员/仓管员/财务/质量管理五个角色模板）。

### BUG-21 列表筛选参数无效

- **现象**：角色权限页与权限管理页都有「关键词」搜索框，输入后点查询结果不变。
- **根因**：`list_roles` / `list_permissions` 未声明 `keyword` 参数，前端传了也被 FastAPI 忽略（既不报错也不过滤）。
- **修复**：两个接口补上 `keyword` 过滤（角色按名称、权限按编码/名称/说明，均下推 SQL 后再分页）。
- **验证**：`GET /api/roles?keyword=临时角色` 只返回匹配项；`GET /api/permissions?keyword=sales:` 只返回 `sales:` 前缀权限。

### BUG-22 高危操作缺少保护与审计

- **现象**：删除/停用最后一个管理员、删除自己、删除仍被账号使用的角色、删除仍被角色引用的权限，全部会成功，
  且系统管理操作除「创建用户」外都不写审计日志。
- **修复**（均返回 400 并说明原因）：

  | 约束 | 提示 |
  | --- | --- |
  | 不能删除/停用当前登录账号 | 不能删除/停用当前登录账号 |
  | 必须保留至少一个可用管理员（删除、停用、给自己摘掉 `all` 三条路径都拦截） | 系统需保留至少一个可用的管理员账号 |
  | `all` 权限不可删除 | 内置「全部权限」不允许删除 |
  | `all` 不可从角色上移除 | 内置「全部权限」不允许从角色上移除，如需降权请改用其他角色 |
  | 角色仍被账号使用不可删除 | 该角色仍分配给 N 个账号，请先解除关联再删除 |
  | 权限仍被角色使用不可删除 | 该权限仍分配给 N 个角色，请先解除关联再删除 |

- **审计**：用户/角色/权限的新增、修改、删除与绑定关系变更均写入 `audit_logs`（`module=system`），可在「操作日志」页查询。

### BUG-23 前端无权限感知

- **现象**：任何账号登录后侧边菜单、可访问路由、页面按钮完全一致。
- **修复**：
  1. `stores/user.ts` 保存 `/auth/me` 返回的权限编码，提供 `hasPermission()`（`all` 通配、支持数组「任一命中」）；
  2. 路由 `meta.permission` + 全局前置守卫：无权限跳转新增的 `/403` 页面（页面会列出当前账号已获权限）；
  3. `MainLayout` 按权限过滤菜单与分组，顶部用户菜单显示当前角色；
  4. 新增全局指令 `v-permission` 与 `CrudPage` 的 `managePermission` 配置项，隐藏无权操作的按钮（21 个页面/组件）；
  5. 角色权限页的「分配权限」改为**按模块分组 + 搜索 + 分组全选**，权限管理页新增「模块」列并支持关键词检索。
